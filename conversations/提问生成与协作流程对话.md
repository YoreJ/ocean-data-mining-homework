## 1. 最容易混淆的概念

### Workflow 与 Agent 的边界

【事实】Workflow 完全可以包含模型判断、条件分支和循环。Anthropic 的一种工程分类把两者区别放在控制权上，Workflow 通过预定义代码路径编排模型和工具，Agent 则由模型动态决定过程与工具使用。这是一种操作性分类，不能仅凭系统名称划分实验组。[Anthropic 官方说明](https://www.anthropic.com/research/building-effective-agents)

【设计建议】两组使用相同的正常执行流程，只替换失败后的决策模块。

| 比较项    | A 组，预编写规则恢复            | B 组，模型动态恢复   |
| ------ | ---------------------- | ------------ |
| 失败前流程  | 相同                     | 相同           |
| 可观察状态  | 任务、工具说明、调用历史、错误返回、剩余预算 | 完全相同         |
| 决策方式   | 已冻结的规则根据当前状态选择行动       | 模型根据当前状态选择行动 |
| 可执行行动  | 相同工具及参数范围              | 相同工具及参数范围    |
| 后续执行   | 共同执行器负责调用、校验和停止        | 同一执行器        |
| 测试期间修改 | 规则冻结                   | 提示词与模型配置冻结   |

A 组应包含合理的重试、参数修复和备用路径。两组都可以使用模型完成其他共同步骤。

尤其需要固定一个边界。**建议让恢复模块持续负责到任务结束**，每次收到工具反馈后重新决策。这测量的是恢复策略。如果仅允许模型选择失败后的第一个动作，则测量范围更窄，应另行命名。

### “调用预算相同”与“成本相同”

【设计建议】分别记录三类资源。

- **工具调用预算**。失败调用、重试、查询元数据均计入。
- **模型调用与 token 用量**。包括输入、输出及服务提供的推理用量。
- **实际成本与耗时**。费用按运行时价格计算，本地模型记录运行时间及硬件。

两组可以拥有相同资源上限，同时实际消耗不同。规则组无需为了用满预算而额外调用模型。

【事实】《AI Agents That Matter》强调联合评估准确率与成本，并指出评测过拟合和复现不足会影响结论。这支持记录上述指标，但没有直接回答你的候选问题。[论文原文](https://arxiv.org/abs/2407.01502)

### “一次调用失败”与“任务失败”

【设计建议】第一版限定为**工具明确返回错误**。工具返回正常状态但内容错误，涉及额外的故障检测能力，应单独研究。

还要区分一次失败事件和一个故障来源。例如，一个数据源持续不可用，可以造成多次调用失败。实验应固定故障持续条件。

## 2. 三个最有力的质疑

### 质疑一，优势可能来自规则组过弱

如果 A 组只会重试，B 组可以查信息、改参数、换路径，那么结果容易受到基线实现质量影响。

**修正办法**

- 给 A 组实现合理的恢复规则，并公开规则表。
- 两组获得相同工具说明与可观察信息。
- 使用开发集完善规则和提示词，随后同时冻结。
- 保留未参与调试的测试集，并记录两组调试投入。

【推测】在错误码清晰、恢复动作唯一的场景中，规则组可能已经接近可达到的上限，模型增加的收益可能很小。这同样是有价值的结果。

### 质疑二，故障分布可能提前决定胜负

如果全部故障都能通过固定重试解决，实验偏向规则策略。如果专门挑选规则未覆盖、但自然语言提示很充分的错误，实验可能偏向模型策略。

**修正办法**

- 事先声明故障类型、比例和可恢复条件。
- 两组使用相同任务与故障计划，并分别重置环境。
- 按故障类型报告结果，避免总体平均值掩盖差异。
- 将“已知故障的新实例”与“未见过的故障机制”分开评价。

【事实】ToolMaze 已把显式／隐式、暂时／持续性工具扰动纳入评测，说明故障结构本身就是重要实验维度。该来源为预印本。[ToolMaze 原文](https://arxiv.org/abs/2606.05806)

### 质疑三，成功率提高可能只是更多计算投入，少量样本也可能产生偶然差异

相同工具调用次数无法控制模型推理成本。只跑少数任务，也容易把模型随机波动当作稳定提升。

**修正办法**

- 比较相同工具预算下的完成率，同时报告模型消耗和耗时。
- 配对运行相同任务，记录“仅 A 成功、仅 B 成功、共同成功、共同失败”。
- 对模型组做重复运行，但统计不确定性时以任务为单位，避免将重复运行当成独立任务。
- 报告完成率差值及置信区间。小样本结果应作为初步证据。
- 在运行前确定“值得”的门槛，例如最低完成率增益、最高额外费用或延迟。

【设计建议】可计算“每多完成一个任务的额外成本”，用两组总成本差除以成功数量差。只有成功数量确实增加时，这个指标才有解释价值。

## 3. 学生可完成的最小实验场景

【设计建议】采用**本地海洋观测数据查询与统计**。我根据当前作业目录选择了海洋数据作为示例，题材可以替换。

### 任务和工具

任务统一为“计算指定站点、指定日期的有效海表温度均值，输出均值、有效记录数及数据来源”。

数据使用本地生成的 CSV。程序预先保存标准答案，具体数值通过工具获取。

| 工具                                 | 功能                     |
| ---------------------------------- | ---------------------- |
| `read_data(source, station, date)` | 从主数据源或镜像读取数据           |
| `inspect_source(source)`           | 查询当前站点标识格式、单位和镜像位置     |
| `summarize(data_handle)`           | 使用固定代码过滤无效记录、计算均值并返回结果 |

主源与镜像包含相同观测数据。统计计算和最终输出格式由两组共用的代码处理，使比较集中在恢复路径上。工具均为本地函数，可以用一个固定模型服务，也可以使用本地模型。

### 失败类型

首次正常流程固定调用主源读取数据，在此处设置三类故障。

| 类型       | 环境行为                             | 可行恢复路径         |
| -------- | -------------------------------- | -------------- |
| 一次性超时    | 首次读取返回 `TIMEOUT`，之后恢复            | 重试             |
| 主源持续不可用  | 本轮主源始终返回 `UNAVAILABLE`           | 切换镜像           |
| 站点标识格式变化 | 旧标识返回 `INVALID_STATION`，错误中不给新标识 | 查询元数据，再用当前格式读取 |

这里的“一次故障注入”表示每个任务只启用一个故障来源，持续不可用可能引起多次失败。故障状态按数据源和任务绑定，避免两组因调用顺序不同遭遇不同环境。

A 组应能根据错误码执行上述合理规则。标识转换可读取元数据中的映射，无需在规则中硬编码测试站点。

### 成功判定和预算

- 均值与标准答案之差不超过预设容差，例如 \\(10^{-6}\\) ℃。
- 有效记录数正确，来源与实际读取记录一致。
- 在预算内结束。预算耗尽、错误输出或未提交均计为失败。
- 每任务最多 **5 次工具调用**，包含首次失败调用。
- B 组在首次失败后最多 **4 次模型决策**，每次最多发出一个工具调用，并设置统一 token 上限。
- 工具封装中的自动重试关闭，所有实际尝试都记账。

最短正常流程是读取、统计两次调用。最复杂的上述恢复路径需要失败读取、元数据查询、重新读取、统计四次调用，5 次预算留有少量调整空间。

### 最小运行规模

建议先用 **12 个开发实例**调试，再冻结配置，测试 **30 个基础任务**。每个任务分别运行三类故障和一个无故障对照，共 120 个条件实例。模型组每个实例重复 3 次。

这足够检查实现、发现明显差异，检测小幅提升所需的样本量仍要根据先导实验估计。首轮结果最多支持所选模型、规则和故障分布下的结论。

规则组能够完整走通这条路径。模型组如果选择相同动作，也会成功。

### 什么选择会影响最终结果

在这个具体案例中，四次预算恰好够用，所以额外调用会影响结果。

- 编号无效后，继续用旧编号查询，会浪费一次调用。
- 主源返回 `NO_RECORD` 后再次查询主源，会浪费一次调用。
- 最后一次机会选择终止，会放弃仍可能成功的重试。

这些差异主要检验控制器能否遵守已知工具约定、利用历史、避免无效动作。合理的规则已经可以处理它们。

主源和备用源的先后顺序，也未必产生差异。如果修正编号后先查备用源，再重试，也可能更早成功。因此，不能把预想的那条执行路径当成唯一正确答案。

**这个案例可以作为实现检查，确认两组能够处理连续失败。它对“模型逐步决策是否带来额外收益”的辨别力很有限。**

## 三、怎样才会出现真正需要权衡的决策

考虑另一个失败现场。

两组都知道标准编号。主源刚刚超时，备用源尚未尝试，只剩一次调用。主源重试和切换备用源都可能成功。

这时，两种选择会在以下条件下影响结果。

| 模拟器中的实际情况      | 重试主源 | 切换备用源 |
| -------------- | ---- | ----- |
| 主源下一次恢复，备用源无记录 | 成功   | 失败    |
| 主源持续不可用，备用源有记录 | 失败   | 成功    |

但这里还有一道关键检查。

### 情况一，两组没有任何线索区分这两种情况

如果可见信息完全相同，那么单次成功可能只说明选择碰巧符合隐藏环境。模型无法仅凭“动态决策”得知隐藏状态。

此时应该比较给定故障分布下的平均表现。规则可以根据开发数据设置“超时后重试优先”或“切换优先”，模型也只能依据它获得的信息选择。测试环境偏向哪种隐藏情况，会直接影响谁更容易获胜。

### 情况二，共同历史提供了相关线索

例如两组都能看到，主源已经连续超时三次，备用源刚刚成功返回过该站点相邻日期的数据。这些信息可能影响选择。

然而，规则也可以利用它们。你可以写出“主源连续超时达到阈值时切换”的策略，还可以根据开发数据调整阈值。

因此，**“动作选择会影响结果”只是必要条件。你还需要解释，这种选择为什么值得交给模型，以及合理规则在什么约束下存在困难。**

如果状态少、工具语义清楚、有效动作有限，规则策略很可能既容易写，也容易验证。把这些条件交给模型，并不会自动产生优势。

- 编号错误提供了明确的参数修复路径。
- 确定缺少记录提供了明确的数据源排除依据。
- 临时超时可以通过有限重试和切换策略处理。

## 一、哪些能够确定拦截

先为当前模拟任务明确两条约定。

- 一次任务使用固定的数据快照，查询不会改变数据或接口状态。
- `NO_RECORD` 只在参数已通过验证后返回，表示指定数据源中，指定站点、日期和变量确实没有记录。

这两条约定让历史中的否定信息能够持续生效。

可以采用下面的判定标准。

> 在所有符合工具约定、且与当前历史一致的环境状态中，该动作都无法取得所请求的有效数据，也无法提供新的相关信息，才允许按“确定无效”拦截。

### 建议先只实现两条历史约束

| 历史证据                  | 拦截条件                               | 容易误拦的反例                           |
| --------------------- | ---------------------------------- | --------------------------------- |
| `INVALID_ID` 明确指出编号无效 | 相同编号被再次用于同一个编号命名空间，且接口约定与状态未变化     | 参数已改成有效编号，应放行。备用源使用另一套编号体系，也应重新判断 |
| 参数有效的查询返回 `NO_RECORD` | 数据源、标准站点身份、日期、变量、数据快照均与已确认无记录的查询一致 | 切换数据源、改变日期或纠正站点身份后，历史证据可能已经不适用    |

这里有两个细节。

**第一，按照错误涉及的范围匹配。**\
如果编号在某个数据源中全局无效，改日期也无法修复它。如果“编号无效”的含义只涉及某个接口，换接口后便需要重新判断。

**第二，按工具定义的语义判断请求是否相同。**\
例如 `S17` 与某个站点别名是否表示同一站点，需要已验证的映射。检查器不能凭字符串相似度合并它们。

### 一组具体反例

假设历史已有两条记录。

1. 主源使用旧编号 `OLD7`，返回 `INVALID_ID`。
2. 查询编号后得到 `S17`，用它查询主源指定日期，返回 `NO_RECORD`。

接下来应当如此处理。

| 模型提出的动作             | 处理     | 依据                       |
| ------------------- | ------ | ------------------------ |
| 再用 `OLD7` 查询主源      | 拦截     | 旧编号在主源仍然无效               |
| 用 `S17` 查询主源相同日期、变量 | 拦截     | 该请求已确认无记录                |
| 用 `S17` 查询备用源       | 放行     | 主源的缺失记录不能推出备用源也缺失        |
| 用 `S17` 查询主源另一日期    | 放行此项检查 | 缺失证据只涉及原日期               |
| 备用源超时后，以相同参数重试      | 放行     | 超时没有证明数据缺失或参数无效          |
| 再查询一次已获得的标准编号       | 暂不纳入拦截 | 可能冗余，但需要另外证明返回完全确定、没有新信息 |

最后一项可以以后研究，第一版保持两条约束就足够。

### 以下情况只能判断“可能不划算”

- 连续超时后继续重试。
- 尚未尝试备用源，却继续查询主源。
- 已经知道标准编号，又查询一次编号。
- 剩余预算很少时，选择一个成功机会看起来较小的动作。

尤其是连续超时。即使连续五次失败，第六次仍可能成功。重试次数上限可以作为所有组共享的执行限制，但它表达的是预算政策。

还有一个很容易忽略的反例。如果一次查询可以触发后台更新、推进恢复状态或等待真实时间过去，即使返回相同错误，重复执行也可能有作用。因此，你的“确定无效”判定依赖前面约定的固定快照与只读查询。

## 二、统一预算，同时把退回成本完整计入

研究改进效果时，主要对照应当是**原始模型控制器与加入检查器的同一模型控制器**。固定规则组仍可保留为原研究问题的参照。

### 两本独立账目

| 项目             | 如何扣减                                |
| -------------- | ----------------------------------- |
| 工具预算 \\(T\\)   | 每次真正提交给模拟工具的调用扣一次，成功、超时、编号错误和无记录都计入 |
| 模型决策预算 \\(D\\) | 每次调用模型生成动作扣一次，包括首次选择和被退回后的重新选择      |

被拦截的动作消耗一次模型决策，工具调用数保持原值。这样恰好体现你要研究的交换关系——付出重选成本，保留工具调用机会。

还应统一以下设置。

- 每次模型调用只提出一个动作。
- 两个模型组使用相同的 \\(T\\)、\\(D\\)、模型设置和单次输出上限。
- 两组都有相同的累计 token 上限，所有重选输入、拒绝反馈和输出都计入。
- 工具或决策预算耗尽后，执行器按统一规则终止，已取得的有效数据直接交给共同判分程序处理。

有了全局 \\(D\\)，无限重选就受到限制。第一版可以只使用这个全局限制，避免再引入每一步的局部重选额度。

**预算上限相同，并不意味着实际成本相同。** 最终仍需分别记录工具调用、模型调用、输入输出 token、检查耗时及总耗时。失败任务消耗的资源也要计入。

### 一个能看清交换关系的例子

假设两组都剩余两次工具调用、三次模型决策。主源已确认无记录，备用源仍可尝试。

两组第一次都提出“重复查询主源”。

| 后续过程  | 原始模型组                | 加检查器组                  |
| ----- | -------------------- | ---------------------- |
| 第一次选择 | 执行无效查询，剩 1 次工具、2 次决策 | 退回，剩 2 次工具、2 次决策       |
| 第二次选择 | 查询备用源，超时，工具预算耗尽      | 查询备用源，超时，剩 1 次工具、1 次决策 |
| 第三次选择 | 已终止                  | 若模型选择重试且成功，则完成任务       |

这说明检查器可能怎样产生收益。另一种结果也完全可能发生——模型被退回后继续提出相同动作，耗尽决策预算，任务仍然失败。

因此，“拦下了几次调用”和“因此多完成了几个任务”需要分别统计。

### 检查器的权限要固定

建议检查器只返回三项信息。

- 命中的约束编号。
- 支持判定的历史记录编号。
- 简短的拒绝原因。

例如，“记录 5 已确认主源对 S17、日期 D 的温度记录缺失，当前请求处于相同数据快照。”

模型负责提出替代动作与参数。检查器只判定当前提案，并保留完整审计记录。

两组的初始工具说明和提示词都应包含相同约定与约束。加入检查器组获得的额外反馈，是对共同历史的即时引用。这也是干预的一部分，所以能够检验的是**拦截加证据反馈的整体机制**。若将来要区分两部分的贡献，才需要额外对照。

另外，退回动作不应推进模拟器的工具调用序列或故障状态。对于只读查询，模拟器也应避免让一次无关的无效调用改变另一个数据源的恢复进程。

## 四、课程作业可以贡献什么

可以把贡献集中到一个具体问题。

> 在结构化错误、固定数据快照和双重预算下，按错误语义及作用范围拦截已知无效动作，能否提高模型恢复的资源利用效率？

其中有三个可验证的主张。

1. **判定正确性。** 两条约束能否准确区分已知无效查询、参数修正后的新查询、切换数据源后的新查询，以及超时重试。
2. **恢复收益。** 节省下来的工具机会，是否被模型用于取得有效结果。
3. **成本交换。** 收益能否覆盖额外模型决策、token 和延迟。

“参数已修正”“数据源已切换”“超时后重试”应当专门用来检查误拦。由于模拟环境很小，可以根据完整工具约定检查这些动作的有效性。评测程序可以使用环境真值，检查器的输入则始终限定为公开约定和历史。

这足以形成课程作业层面的独立探索，算法原创程度应据实表述。

| 实验结果                      | 应当承认的结论                    |
| ------------------------- | -------------------------- |
| 原始模型几乎从不提出这两类无效动作         | 当前任务里缺少需要干预的实际问题           |
